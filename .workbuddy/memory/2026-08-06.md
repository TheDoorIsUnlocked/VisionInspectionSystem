## XDG0010 持续不消失——提取独立资源字典（第二轮修复）

## 实例分割掩膜（yolov8s-seg）不显示区域——同一类 bug，掩膜没画
- 用户问 yolov8s-seg 检测什么、为什么看不到区域。答：seg 是实例分割，检测同 80 类 COCO 物体但额外输出像素级掩膜（物体精确轮廓）。框有了但没掩膜 = 同 pose 的"数据有、没画"问题。
- **YoloDotNet 关键事实**（本地项目 `../YoloDotNet/Models/Segmentation.cs`，非 nuget）：
  - `Segmentation` 类**只有** `Label/Confidence/BoundingBox/BitPackedPixelMask` 四个属性，**没有 `Mask` 这个 SKBitmap 属性**（一度误以为有 `r.Mask`，编译直接报错 CS1061）。
  - 掩膜是 `BitPackedPixelMask`（`byte[]`），**尺寸 = 边界框宽高（不是整图）**。位序：`byteIndex = i>>3; bitIndex = i&7; isOn = (packed[byteIndex] & (1<<bitIndex)) != 0`（见 `Extensions/ImageExtension.cs` 的 `UnpackToBitmap`）。
  - 官方自带 `UnpackToBitmap(this byte[], int width, int height)` 扩展方法（在 `YoloDotNet.Extensions`，unsafe），解出白(255)/黑(0)掩膜，再用 `CreateGrayscaleToColorFilter` + `BlendMode.SrcOver` 上色绘制到 `box.Left/box.Top`。
- 修复（不依赖 `YoloDotNet.Extensions`，自包含）：
  - `DetectedObject.Mask` 保持 `byte[]?`（存 `r.BitPackedPixelMask`）。
  - 新增 `DrawSegmentationMask(canvas, packedMask, boxX, boxY, boxW, boxH, color)` + `unsafe UnpackSegmentationMask(packed, w, h, color)`（UI csproj 已开 `AllowUnsafeBlocks`）。解包时直接写彩色半透明像素（调色板 `SEG_MASK_COLORS` 按 `ClassId%8` 取色，alpha=110），`canvas.DrawBitmap(maskBmp, boxX, boxY)`。
  - 两重载都加调用：重载1 用 `obj.PixelBoundingBox` 的 Left/Top/Width/Height；重载2 用 `obj.BoundingBox[0..3]`。
- 验证：dotnet build 0 错误（注意 `UnpackSegmentationMask` 方法要标 `unsafe`；循环内 `var color` 与重载1 已有的框颜色 `color` 冲突，改名叫 `maskColor`）。
- **教训**：用本地 YoloDotNet 源码核实 API 再写代码，别凭记忆（`Segmentation` 没有 `Mask` 属性）；位打包掩膜尺寸是 bbox 不是整图，绘制位置要用 bbox 左上角。

## 修复：选择模型时报 "String '5' was not recognized as a valid DateTime"
- 根因：SQLite `ALTER TABLE ADD COLUMN` 会把新列追加到表末尾，而 `GetAllModelsAsync` / `GetModelAsync` 之前用**硬编码列索引**读取。旧数据库升级后列顺序与 `CREATE TABLE` 不一致，导致把 `SmoothMaxMissed=5` 读成了 `CreatedAt`，触发 DateTime 解析异常。
- 修复：将 `ModelManager` 中两个读取方法全部改为按**列名**读取（`reader.GetOrdinal("ColumnName")`），不再依赖列顺序。
- 验证：dotnet build 0 错误。
- **教训**：数据库读取务必用列名，绝不用硬编码索引；`ALTER TABLE` 追加列会改变物理顺序。

## 修复：实时 bbox "原地高频闪烁"（真正的根因，非参数问题）
- 用户按推荐参数（EMA=0.10 等）仍闪，排查确认**参数已正确传入** smoother（`LoadModelAsync` 重建 `_realtimeSmoother` 用的是 `_loadedModel` 的 4 个参数，字段非 readonly 可赋值）。
- 真正的两个算法缺陷（`DetectionTrackSmoother`）：
  1. **跟踪匹配只认纯 IoU > 阈值（默认 0.30）**：框原地抖动时相邻帧 IoU 常掉到 0.30 以下 → 匹配失配 → 每帧重建轨道，EMA 永远不积累，框跳。
  2. **显示条件依赖 `HitCount >= confirmHits` + 失配时 `HitCount=0` 重置**：已显示的框一旦偶发失配（抖动），`HitCount` 被清零 → 当帧不显示 → 下一帧匹配上又显示 → 框"忽隐忽现/高频闪烁"。
- 修复：
  - 新增 `MatchScore`：综合 IoU + **中心点归一化距离** + **尺寸相似度**，抖动场景（中心点基本不动、尺寸不变）也能稳定匹配上。原 `_iouThreshold` 参数现作为"综合匹配分阈值"语义保留。
  - `Track` 增加 `EverConfirmed` 标志：连续命中 `confirmHits` 帧后置 `true`；`GetActiveBoxes`/`GetActiveObjects` 显示条件改为 `EverConfirmed`（而非当前 `HitCount>=confirmHits`）；失配分支**不再重置 `HitCount`**，已确认轨道只在 `MissedCount>maxMissed` 时才删除 → 偶发失配框不再消失。
- 验证：dotnet build 0 错误（注意 `MathF.Clamp` 在此 TFM 不可用，改用 `Math.Clamp`）。
- **关键教训**：bbox 时序平滑的"匹配"不能只靠 IoU；对抖动场景必须叠加中心点距离/尺寸相似兜底，否则平滑器形同虚设。显示条件要区分"首次确认"与"续显"，失配不应立即隐藏已确认目标。
- 用户当前参数可保持（EMA 0.10~0.20、跟踪IoU 0.30 足够）；若仍想要更跟手可调高 EMA。

  - 相机帧率(如30fps) >> 实时推理频率(如10fps)，导致屏幕在「无框原始帧」与「有框帧」之间高频交替 = 用户看到的"bbox 闪烁/时有时无"。
  - SOP 丝滑原因：SOP 在 `OnCameraImageGrabbed` 里**直接把 `_lastSopResult` 叠加到最新相机帧再设 CurrentImage**，每帧都有框，且 `_lastSopResult` 是 `_detectionSmoother` 平滑后的，配合老化机制 → 丝滑。
- 修复（让实时检测**复用 SOP 渲染架构**）：
  1. 提取 `DrawDetectedObjects(SKCanvas, List<DetectedObject>, float textSize)` 绘制核心（从 `DrawDetectionResults` 抽出），供叠加复用。
  2. 新增字段 `_lastRealtimeObjects`（缓存最近平滑结果）、`_noRealtimeResultFrameCount`、常量 `MaxNoRealtimeResultFrames=15`（老化）。
  3. `PerformRealTimeDetectionAsync`：**不再**在推理后设置 `CurrentImage`，改为把 `smoothed` 写入 `_lastRealtimeObjects` 并重置老化计数（缓存）。
  4. `OnCameraImageGrabbed`：SOP 块之后，若 `IsRealTimeDetecting && _lastRealtimeObjects != null`，在 skBitmap 上 `DrawDetectedObjects` 叠加，并做老化计数（超过 15 帧无新结果清空缓存）。
  5. `StopRealTimeDetection`：清空 `_lastRealtimeObjects` 与老化计数。
- 验证：dotnet build 0 错误。
- **关键教训**：WPF 相机实时叠加必须"每帧在最新帧上叠加缓存结果后统一设 CurrentImage"，绝不能"先设无框原始帧、推理完再设带框帧"——后者在帧率不匹配时必然闪烁。SOP 与实时检测应共用同一渲染管线。

## 修复：cup SOP 拿起动作过松 + 跳步检测假阳性
- 现象：

  2. 开始检测后频繁报 `[SkipStep] 可能跳过了步骤 'XXX'，直接满足后续步骤 '完成'`。
- 根因 1（拿起过松）：`StepConditionEvaluator.HandMoveFromTo` 在 `hasFrom && !hasTo`（pickup）分支里，把"手正拿着目标物体"（`handHoldingTarget`）作为**最高优先级**判定，且不要求手曾访问 `from_region`。只要画面里手碰到 cup，就视为"拿起"。

## 优化：DWPose 横伸/远离躯干手部识别率低
- 现象：手横向伸出（如去拿杯子）或远离躯干时，DWPose 完全识别不到手，导致 `hand_action` 步骤无法推进；同时因手部缺失，出现 false skip 违规。
- 根因：DWPose 是全身姿态模型，手部关键点（COCO-WholeBody 91-112/113-134）是全身姿态的附加输出。手一旦远离躯干、角度特殊或被遮挡，关键点置信度骤降，验证过滤后直接丢弃。
- 优化：新增 `YoloPose` 手部检测后端，即 `YoloPoseHandEstimationService`（已存在但未接入）。流程为 `YOLOv8-pose/yolov11s-pose` 检测手腕 → 以手腕为中心裁切 200×200 区域 → 用已有的 `hand_landmark_sparse_Nx3x224x224.onnx` 精修 21 点手指关键点。该方案对横伸手、远离躯干的手通常比 DWPose 更稳，且不需要下载新模型。
- 实现：
  - `HandDetectionBackend` 枚举新增 `YoloPose = 4`。
  - `SOPModule.InitializeHandPoseEstimationAsync` 增加 `YoloPose` 分支，并在 `Auto` 回退链中放在 `YOLO-hand` 之后、`DWPose` 之前：`MediaPipe → YOLO-hand → YoloPose → DWPose`。
  - `sop_config.json` 的 `HandDetectionBackend` 从 `"DWPose"` 改为 `"YoloPose"`，用户重启后即生效。
- 注意：YoloPose 每帧都要跑一次 YOLO-pose + 每只手一次 Landmark 推理，计算量高于 DWPose；若后续出现明显卡顿，可改为跳帧推理或切回 `DWPose`。
